# 1. The Next Phase of 'Rollup-Centric Ethereum'

The Dencun upgrade introduced EIP-4844, which provides a dedicated space called blobs for rollup data, significantly reducing L2 fees. Ethereum's strategy of providing data availability while rollups execute transactions on top has resulted in tangible benefits for users.

However, simply increasing data space is not enough to accommodate more transactions. It is necessary to reduce the burden of data transmission and transaction execution and manage the ever-growing state database. Additionally, in an environment where block production is concentrated among specialized builders, mechanisms are needed to ensure that valid transactions are not arbitrarily excluded.

Ethereum addresses these challenges at different levels through a hard fork roadmap starting with Fusaka, followed by Glamsterdam and Hegotá. Fusaka lays the groundwork for data availability expansion and execution safeguards. The subsequent Glamsterdam aims to improve block production, execution, and verification structures, while Hegotá focuses on strengthening transaction inclusion rules and native account abstraction. This article examines how Ethereum plans to expand processing capacity while addressing node operation burdens and trust issues through these three upgrades.

The table below shows the status of major proposals as of October 8, 2026. Specifications and schedules for subsequent upgrades may change.

# 2. Fusaka

> "Blob capacity expansion for L2 rollup chains and securing L1 execution safety"

## ① PeerDAS: P2P Subnet-Based Blob Expansion

Under the EIP-4844 system, all validator nodes had to download the entire blob data directly, making it difficult to increase blob generation indefinitely due to network bandwidth limitations.

With the application of PeerDAS (Peer Data Availability Sampling), nodes receive only 'partitioned fragments' through P2P subnets instead of the entire data and confirm the availability of the entire data through random sampling. This reduces the bandwidth burden per node compared to downloading all data, supporting more blobs. Actual requirements vary depending on the node's role and throughput.

- **1D Reed–Solomon Erasure Coding**: Adds recovery data to each blob and divides it into cells. A column is formed by grouping cells at the same position across multiple blobs.
- **Utilizing P2P Subnets**
  - The Ethereum consensus network uses subnets to distribute messages so that not all nodes receive all messages.
  - PeerDAS distributes columns across subnets. Nodes store their assigned columns and request samples of other columns from peers to verify availability.

[EIP-7594: PeerDAS - Peer Data Availability Sampling](https://eips.ethereum.org/EIPS/eip-7594)

## ② BPO (Blob Parameter Only)

EIP-7892 adjusts blob capacity through small hard forks without waiting for major feature upgrades. Instead of adding new protocol operations, it changes existing blob parameters. Nodes must use client versions with agreed settings and activation schedules.

- Blob Target (`target`): The target average number of blobs per block, serving as the basis for fee adjustments.
- Blob Limit (`max`): The maximum number of blobs allowed per block.
- Blob Base Fee Update Fraction (`baseFeeUpdateFraction`): Adjusts the speed at which the base blob fee responds to usage changes.

Increasing `max` allows for temporary demand surges, while increasing `target` accommodates more average usage. Generally, exceeding the target usage raises fees, while usage below the target lowers them. However, Fusaka's [EIP-7918](https://eips.ethereum.org/EIPS/eip-7918) corrects this behavior when blob fees are lower than execution costs.

[EIP-7892: Blob Parameter Only Hardforks](https://eips.ethereum.org/EIPS/eip-7892)

## ③ Transaction Gas Limit Cap

Fusaka limits the `gasLimit` specified for a single transaction to `16,777,216 (2^24) gas`.
This prevents DoS attacks caused by a single transaction monopolizing the entire block's computational resources, ensures fair gas allocation among transactions within a block, and prevents excessively long block verification times, facilitating smooth node synchronization.

Even if the actual consumption is lower, **the specified `gasLimit` itself must meet the cap.** For example, if only 1,000,000 gas is needed for execution, specifying `gasLimit = 20,000,000` for leeway will result in transaction rejection.

[EIP-7825: Transaction Gas Limit Cap](https://eips.ethereum.org/EIPS/eip-7825)

# 3. Glamsterdam

> Internalizing the block production system previously reliant on external middleware into the L1 protocol and reorganizing the EVM execution structure for parallel processing

## ① ePBS (Enshrined Proposer-Builder Separation)

In the existing PBS structure, proposer-builder separation was implemented through middleware called MEV-Boost outside the protocol.

- MEV-Boost Middleware
  - The flow of MEV-Boost can be simplified as follows:
  `builder가 relay에 블록 페이로드 및 입찰 제출 -> relay가 블록 유효성 검증 -> proposer가 blinded block 선택 -> relay가 페이로드 제공`
  - Concerns included builders sending invalid blocks or proposers preemptively viewing and stealing completed block contents.
  - A third-party '**relay**' acts as an intermediary between the proposer and builder, relying on trust.
  - The relay verifies block validity, shows the block payload header and bid price to the proposer, and provides the payload upon the proposer's signature.

Since relays operate as centralized servers outside the protocol, they can become centralized or experience failures. In case of failure, connecting to another relay is possible, but it is considered a risk factor in the block proposal process.

EIP-7732 **ePBS** (Enshrined PBS) eliminates the relay from the existing MEV-Boost structure and 'enshrines' the core intermediary role performed by the relay into the Ethereum consensus layer code.

[EIP-7732: Enshrined Proposer-Builder Separation](https://eips.ethereum.org/EIPS/eip-7732)

## ② BALs: Foundation for EVM Parallel Processing

The existing EVM executed transactions sequentially, applying state changes one by one. Before executing a transaction, it was unknown which storage slots would be accessed and changed, making it difficult to utilize multicore parallel processing when processing a single block, even if nodes had multiple CPU cores.

BALs (Block Access Lists / EIP-7928) involve the block builder summarizing and including a hash of access targets (accounts, storage slots, etc.) at the block level in the block header and body. When validator nodes receive a block, they refer to BALs to identify transaction groups without storage conflicts and distribute them across multiple CPU cores for parallel execution.

```
            [ 병렬 작업 배분의 단순화된 예시 ]
                           │

   ┌───────────────────────┼───────────────────────┐
   ▼                       ▼                       ▼

  [ Group A ]             [ Group B ]             [ Group C ]
  Tx 1, Tx 3 (상태 A 접근)   Tx 2 (상태 B 접근)      Tx 4, Tx 5 (상태 C 접근)
  │                       │                       │
  Core 1 실행             Core 2 실행             Core 3 실행
  └───────────────────────┼───────────────────────┘
                          ▼
                    [ 상태 최종 적용 ]

```

[EIP-7928: Block Access Lists](https://eips.ethereum.org/EIPS/eip-7928)

## ③ Gas Model Overhaul: Separating Execution/State Resources

In Glamsterdam, the gas fee mechanism is also overhauled. Gas used for execution and state creation is measured separately. While applying the **EIP-7825** cap from Fusaka to execution gas, a separate state gas budget is allowed within the overall transaction cap.

The design aims to curb long-term state bloat by imposing relatively high gas costs on operations that permanently occupy the node's disk space, such as new account creation or storage slot allocation.

[EIP-8037: State Creation Gas Cost Increase](https://eips.ethereum.org/EIPS/eip-8037)

# 4. Hegotá

> Enhancing transaction inclusion and supporting native account abstraction

## ① FOCIL (Fork-choice enforced Inclusion Lists)

Entrusting block composition to specialized builders reduces the burden on validators, but if a few builders dominate block production, the authority to decide transaction inclusion in blocks is also concentrated. Even if they repeatedly exclude specific transactions, it is difficult to prevent this with existing verification if the remaining transactions are valid. ePBS does not directly address this transaction selection issue.

Under the ePBS system, high-performance builders may intentionally exclude or censor specific transactions. To prevent this, a policy called FOCIL is introduced.

FOCIL involves multiple validator committees, randomly selected, each observing the mempool and creating an **Inclusion List** of transactions that must be included.

In FOCIL, block validity verification is linked to the attester's voting actions. Attester nodes verify whether the block proposed by the builder meets the requirements based on their Inclusion List. If the builder unjustifiably excludes transactions from the list, the attester does not cast a proof vote for that block. Blocks that do not receive votes are naturally not selected as canonical blocks in the chain due to fork choice rules.

[EIP-7805: Fork-choice enforced Inclusion Lists (FOCIL)](https://eips.ethereum.org/EIPS/eip-7805)

## ② Frame Transactions: Native Account Abstraction Including Gas Payment Approval

ERC-4337 supports smart accounts by combining on-chain EntryPoint with a separate mempool and bundler. Pectra's EIP-7702 allows EOA to delegate execution to contract code until changed or revoked. Hegotá's Frame Transactions proposal extends account abstraction to a native transaction format.

EIP-8141 organizes multiple frames for verification, gas payment approval, and execution in sequence. Below is a simplified flow example, not a fixed two-frame structure.

```

[ Frame Transaction (EIP-8141)의 단순화된 예시 ]
┌────────────────────────────────────────────────────────┐
│  1. Validation Frame                                   │
│     - 서명 검증 (P-256 / 패스키 등 커스텀 로직)               │
│     - 가스 지불 승인 (대납 및 선택적 토큰 정산 로직)       │
├────────────────────────────────────────────────────────┤
│  2. Execution Frame                                    │
│     - 실제 DApp 호출 및 상태 변경 연산                       │
└────────────────────────────────────────────────────────┘

```

- **Validation Frame**
  - Executes approval logic such as account signature and spending limits before executing tasks on behalf of the sender. Verification applies not only before inclusion but also during block execution.
  - Executes with the `APPROVE` command to approve execution, gas payment, or both. Approval is not granted solely by returning `True`.
- **Execution Frame**
  - Once approval is complete, logic for actual token transfers or smart contract calls is executed.

Frames support custom signature verification, including Fusaka's P-256 precompile, and third-party gas payment approval, without requiring ERC-4337's separate bundler infrastructure. Protocol gas fees are still paid in ETH, while alternative token settlements are handled by application logic.

[EIP-8141: Frame Transactions](https://eips.ethereum.org/EIPS/eip-8141)

# 5. Remaining Challenges After Expansion

Even with the ongoing reforms through Fusaka, Glamsterdam, and Hegotá, there are continuous challenges in the Ethereum ecosystem that require evaluation.

1. **Concentration in the Builder Layer**: Although ePBS reduces relay dependency in the block proposal process, the block production market may still concentrate among a few specialized builders with high-performance MEV algorithms and large capital.
2. **Node Operation Resource Burden**: PeerDAS and BALs improve efficiency, and BPO allows for verified step-by-step capacity adjustments. As throughput increases, bandwidth, CPU, and memory burdens may grow, necessitating evaluation of small-scale node operations.
3. **Security and Decentralization of L2**: Regardless of L1's data availability and execution performance improvements, the decentralization level of sequencers used by each L2 chain and the completeness of Fraud/Validity Proof systems are areas that need separate verification and evaluation within the L2 ecosystem.

# 6. Summary

- **Fusaka**: Expands **data availability space for L2** through PeerDAS and BPO (EIP-7892) and establishes L1 execution safety with EIP-7825.
- **Glamsterdam**: Internalizes **coordination between proposer and builder into the protocol** with the planned ePBS (EIP-7732) and refines the **EVM parallel execution foundation** with BALs (EIP-7928) and gas overhaul (EIP-8037).
- **Hegotá**: Complements **censorship resistance rules** with the planned FOCIL (EIP-7805) and establishes a **native account abstraction system including gas payment approval** with Frame Transactions (EIP-8141).
