Last week's central pattern is that **security risk is moving from individual applications into shared infrastructure layers**. The Cosmos EVM and Ledger Secure SDK incidents show how a single module reused by many chains or applications can create a broad attack surface.

At the same time, Monad and TRON are making account authentication and execution environments more modular. Wallet, DeFi, dApp, custody, and chain-infrastructure products increasingly need to **manage authentication methods and security posture as separate concerns**.

## 1. A Cosmos EVM vulnerability was exploited across six chains

According to the Cosmos Labs [post-mortem](https://github.com/cosmos/security/blob/main/communications/cosmos_evm_GHSA-7g4w-cg88-2cq2_post_mortem.md), attackers exploited `GHSA-7g4w-cg88-2cq2` from August 20 through 25 to steal funds from several Cosmos-based chains. The flaw was a **missing balance-underflow guard** in the shared Cosmos EVM `StateDB`.

> Missing balance-underflow guard: a vulnerability where a balance subtraction is not checked for a negative result, allowing the negative value to be converted into a very large positive number.

Under specific vesting and delegation flows, the EVM-side spendable balance became abnormally large and allowed an attacker to move funds that did not exist.

The affected releases are `<0.6.2` and `0.7.0–0.7.1`; fixes are included in `0.6.2` and `0.7.2+`. The Cosmos security team coordinated with roughly 40 chains, and six networks were known to have been exploited.

### Why it matters

The incident demonstrates how **one shared module in a modular chain can affect multiple networks at once**—a shared-module blast radius. A chain can have sound application code and still inherit a critical accounting defect from an upstream execution layer.

### Product / engineering implications

**Wallet:** Chain-support pipelines should treat runtime and module versions as security metadata, not merely compatibility metadata. A registry-driven wallet should be able to surface vulnerable `cosmos/evm` versions, chain halts, emergency upgrades, and temporary disable states.

**DeFi / protocol:** An application audit alone cannot cover upstream execution-layer risk. Teams should add the target chain's module version and security advisories to release gates, while independently monitoring invariants such as unexpected balance or supply changes.

**Chain / infrastructure:** Operators of shared modules need to produce a software bill of materials and an affected-chain inventory quickly. Vulnerability notices, validator upgrades, and halt status should also be available as machine-readable state for downstream services.

### Follow-up

- [Wallet] Audit the deployed `cosmos/evm` version on supported chains and verify emergency warning and disable paths.
- [DeFi / protocol] Connect chain module versions to release gates and review balance and supply invariant alerts.
- [Chain / infrastructure] Evaluate a machine-readable security feed for affected scope and upgrade or halt status.

## 2. Shared Ledger SDK vulnerability: a mismatch between what is displayed and what is signed

Ledger's [LSB-023](https://donjon.ledger.com/lsb/023/) describes a flaw that allowed a malicious host to interleave another APDU command—a low-level instruction sent from wallet software to a Ledger device—while a user was reviewing the first operation. In vulnerable applications, signing parameters could change after display, allowing a user to review Transaction A but sign parameters from Transaction B. Ledger reported no evidence of exploitation at disclosure.

The important point is that the issue was in the **shared Ledger Secure SDK**, rather than device firmware. The correction landed in `v26.6.1`, and affected applications must be rebuilt and republished against that SDK. A firmware update alone does not deliver the fix.

### Why it matters

This is a reminder that a hardware-wallet screen cannot be treated as an absolutely trustworthy boundary. Command sequencing and state transitions between the host and application are equally important.

### Product / engineering implications

**Wallet / custody:** Clients need strict APDU sequencing and an explicit signing state machine. They should manage minimum supported Ledger App versions as well as firmware versions. The review surface expands further when swaps, plugins, simulation, clear signing, and blind signing interact.

**DeFi / dApp:** Even when a product provides transaction simulation or a human-readable preview, it must verify that the same calldata and authorization scope reach final device confirmation. A mismatch between dApp intent and the payload interpreted by the hardware application should be observable as an error.

**Exchange / signing infrastructure:** Organizations using hardware signers for withdrawals, treasury operations, or validators cannot determine patch status from firmware inventory alone. Device application versions and deployed SDK lineage belong in the asset inventory.

### Follow-up

- [Wallet / custody] Validate firmware and application versions separately and enforce a minimum application-version policy.
- [DeFi / dApp] Add end-to-end tests showing that the payload sent to the device cannot change after simulation or preview.
- [Exchange / signing infrastructure] Track application versions and SDK lineage for devices in production.

## 3. Monad proposed an account model that separates address from authentication

Monad published the **Flexible and Upgradeable Account Authentication** draft. The design would allow an account to add, replace, or retire authenticators while retaining its address. The reported draft contemplates key rotation, passkeys, multisig recovery, social recovery, and migration to post-quantum signature schemes. It remains an [early draft](https://cryptodaily.co.uk/2026/08/monad-wallet-key-rotation-without-address-change), with implementation details and consensus work still ahead.

### Why it matters

These capabilities are usually implemented through smart accounts or account abstraction. Monad's approach explores moving them into the protocol-level account model. The address becomes persistent identity, while authentication becomes replaceable configuration.

### Product / engineering implications

**Wallet / custody:** Products may eventually need to treat an account as `address + authentication configuration` rather than an `address ↔ private key` pair. Keeping recovery UX, key export, passkeys, hardware signers, and transaction-authorization APIs modular will make that transition easier.

**DeFi / dApp:** An address and its positions may persist while its authentication method changes, but authority and finality during that transition create a distinct risk. Recent authentication changes could become a policy signal for high-value actions, allowance updates, or governance votes.

**Identity / infrastructure:** Indexers and account APIs will need to represent authenticator sets, recovery authority, and pending changes rather than a single public key. Analytics and compliance tooling built around EOA assumptions must also interpret the authentication history of a persistent address.

### Follow-up

- [Wallet / custody] Review recovery authority, authentication-change delays, and downgrade protection.
- [DeFi / dApp] Consider whether high-risk actions need limits or additional confirmation immediately after an authentication change.
- [Identity / infrastructure] Determine how existing EOA-compatible tooling will interpret authenticator history and pending changes.

## 4. A malicious Firefox wallet-extension campaign shows impersonation at industrial scale

Socket's [investigation](https://www.socket.dev/blog/firefox-crypto-wallet-theft) tracked 77 Firefox extension identities linked by shared code and infrastructure, and confirmed wallet- or credential-stealing behavior in 40 of them. The extensions impersonated products including OKX, Rabby, and TronLink, harvesting seed phrases and private keys or serving phishing interfaces from remote content. Socket calls the campaign the **Offside Wallet Theft Factory**.

### Why it matters

The attack model goes beyond cloning a phishing website. Attackers reuse extension identities and version histories, clone open-source wallet code, and replace behavior through remote infrastructure. An official extension-store listing is no longer a sufficient trust signal.

### Product / engineering implications

**Wallet:** Publisher authenticity is itself a product surface. Teams should provide verified install links on official sites, publish canonical extension IDs, explain provenance in-product, and consider detection of conflicting or fake providers.

**DeFi / dApp:** A connected provider can imitate the name and API of a well-known wallet, so provider injection alone cannot establish trust. High-risk transactions should re-confirm origin, chain, spender, and simulation results, while wallet-selection screens should point to official installation paths.

**Platform / security:** Extension marketplaces and browser-security teams need campaign-level detection that combines publisher identity, code similarity, remote-content dependencies, permission changes, and version history. Removing individual listings does not stop variants using the same infrastructure.

### Follow-up

- [Wallet] Check that installation funnels and support documents expose canonical extension IDs.
- [DeFi / dApp] Add provider provenance and high-risk transaction reconfirmation to the connection threat model.
- [Platform / security] Evaluate linked-extension blocking based on shared code, permissions, and remote infrastructure.

## 5. TRON expanded EVM compatibility and passkey-relevant primitives

TRON's mandatory [GreatVoyage `v4.8.2 (Pyrrho)`](https://github.com/tronprotocol/java-tron/releases/tag/GreatVoyage-v4.8.2) node upgrade brings TVM closer to the Ethereum Pectra and Osaka execution environments. It includes a signature-verification precompile for the `secp256r1`/P-256 curve used by WebAuthn and passkeys, Apple Secure Enclave, and Android Keystore. TRON's [release documentation](https://tronprotocol.github.io/documentation-en/releases/versions/v4.8.2/) describes the Pectra/Osaka alignment and related precompile changes.

TRON is also proposing interfaces for address-less signature verification and cross-chain messaging. [TIP-7913](https://github.com/tronprotocol/tips/issues/7913) concerns flexible signature verifiers, while [TIP-7786](https://github.com/tronprotocol/tips/issues/7786) concerns a common cross-chain messaging gateway.

### Why it matters

Non-Ethereum chains are increasingly adopting Ethereum-compatible primitives rather than retaining fully separate execution semantics. That is a signal to abstract multichain wallet functionality around capabilities instead of chain names.

### Product / engineering implications

**Wallet / custody:** Rather than proliferating branches such as `if (chain === "tron")`, a product can expose capabilities such as `supportsPasskey`, `supportsEvmSigning`, and `supportsSmartAccount`. EVM transaction and authentication abstractions can increasingly sit behind a thinner chain-specific adapter.

**DeFi / dApp:** If the cost and calling convention of P-256 verification stabilize, teams can design passkey-based onboarding or session authorization on TRON. Precompile support must still be distinguished from a product-ready account flow with recovery, replay protection, and relayer UX.

**Infrastructure / cross-chain:** A capability such as `supportsCrossChainMessaging` must express more than interface availability: mainnet activation, gateway implementation, message finality, replay protection, and domain separation matter. A standards proposal and production support are not the same state.

### Follow-up

- [Wallet / custody] Define the reusable EVM signing and authentication boundary for a TRON integration.
- [DeFi / dApp] Prototype the cost, recovery model, and replay protection of a passkey flow built on the P-256 precompile.
- [Infrastructure / cross-chain] Track mainnet activation and implementation maturity of passkey-verification and cross-chain messaging primitives separately.

## This week's priorities

The most immediate task is auditing Cosmos EVM exposure. Wallets, deployed DeFi protocols, indexers, bridges, and validator infrastructure all need to verify upstream module versions and emergency-response status. Ledger SDK remediation comes next: wallets, custody providers, exchanges, and connected dApps must revisit the assumption that the hardware-wallet display defines the entire trust boundary.

The larger trend is the decoupling of account identity from keys and the movement toward passkeys and programmable authentication. The exposure differs by product, but keeping **chain representation → transaction execution → authentication/signing → security health state** as separate layers is becoming a shared design concern across wallets, DeFi, custody, and infrastructure.
