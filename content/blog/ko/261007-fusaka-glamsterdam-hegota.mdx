# 1. '롤업 중심 이더리움'의 다음 단계

Dencun 업그레이드가 도입한 EIP-4844는 롤업 데이터를 위한 전용 공간인 blob을 제공해 L2 수수료를 크게 낮췄다. 이더리움이 데이터 가용성을 제공하고, 롤업이 그 위에서 거래를 실행하는 '롤업 중심' 확장 전략이 사용자에게 체감되는 성과로 이어진 것이다.

하지만 더 많은 거래를 수용하려면 데이터 공간을 늘리는 것만으로는 충분하지 않다. 데이터 전송과 거래 실행에 드는 부담을 줄이고, 계속 커지는 상태 데이터베이스도 관리해야 한다. 동시에 블록 생산이 전문 builder에게 집중되는 환경에서 유효한 거래가 자의적으로 배제되지 않도록 하는 장치도 필요하다.

이더리움은 Fusaka를 시작으로 Glamsterdam, Hegotá로 이어지는 하드포크 로드맵을 통해 이러한 과제를 서로 다른 층위에서 다룬다. Fusaka는 데이터 가용성 확장의 기반과 실행 안전장치를 마련했다. 뒤이어 계획된 Glamsterdam은 블록 생산과 실행, 검증 구조를 개선하고, Hegotá는 거래 포함 규칙과 네이티브 계정 추상화를 강화하는 방향으로 이어진다. 이 글에서는 세 업그레이드를 통해 이더리움이 처리 용량을 확대하면서 노드 운영 부담과 신뢰 문제를 어떻게 함께 다루려 하는지 살펴본다.

아래 표는 2026년 10월 8일 기준 주요 제안의 상태다. 후속 업그레이드의 포함 예정 사양과 일정은 변경될 수 있다.

# 2. Fusaka

> "L2 롤업 체인들을 위한 Blob 용량 확장과 L1 연산 안전성 확보"



## ① PeerDAS: P2P 서브넷 기반의 Blob 확장

EIP-4844 체제에서는 모든 validator 노드가 blob 데이터 전체를 직접 다운로드해야 하므로, 네트워크 대역폭 한계로 인해 blob 생성량을 무제한 늘리기 어려웠다.

PeerDAS(Peer Data Availability Sampling) 적용 이후로는 노드가 전체 데이터 대신 P2P 서브넷을 통해 '분할된 조각'만 분담 수신하고, 무작위 샘플링을 통해 전체 데이터의 가용성을 확인한다. 모든 데이터를 내려받는 방식보다 노드당 대역폭 부담을 줄여 더 많은 blob을 지원한다. 실제 요구 사양은 노드 역할과 처리량에 따라 달라진다.

- **1D 리드-솔로몬(Reed–Solomon) 소거 코딩**: 각 blob에 복구용 데이터를 추가하고 cell로 나눈다. 여러 blob의 같은 위치에 있는 cell들을 묶은 것이 column이다.
- **P2P 서브넷** 활용
  - 이더리움 합의 네트워크는 모든 노드가 모든 메시지를 받지 않도록 서브넷을 활용해 메시지를 나눠 전파한다.
  - PeerDAS는 column을 서브넷에 분산한다. 노드는 자신에게 할당된 column을 보관하고, 다른 column의 샘플을 피어에게 요청해 가용성을 확인한다.

[EIP-7594: PeerDAS - Peer Data Availability Sampling](https://eips.ethereum.org/EIPS/eip-7594)

## ② BPO (Blob Parameter Only)

EIP-7892는 대형 기능 업그레이드를 기다리지 않고 작은 하드포크로 blob 용량을 조정하는 방식이다. 새로운 프로토콜 동작을 추가하는 대신 기존 blob 파라미터를 변경한다. 노드는 합의된 설정값과 활성화 일정이 포함된 클라이언트 버전을 사용해야 한다.

- Blob Target (`target`): 블록당 목표 평균 blob 개수. 수수료 조정의 기준이다.
- Blob Limit (`max`): 한 블록에 허용하는 최대 blob 개수.
- Blob Base Fee Update Fraction (`baseFeeUpdateFraction`): 사용량 변화에 blob 기본 수수료가 반응하는 속도를 조절한다.

`max`를 올리면 일시적인 수요 급증을 수용할 여유가 늘고, `target`을 올리면 더 많은 평균 사용을 수용한다. 기본적으로 목표 초과 사용은 수수료를 올리고 목표 미만 사용은 내리는 방향으로 작용한다. 다만 Fusaka의 [EIP-7918](https://eips.ethereum.org/EIPS/eip-7918)은 blob 수수료가 실행 비용에 비해 낮을 때 이 동작을 보정한다.

[EIP-7892: Blob Parameter Only Hardforks](https://eips.ethereum.org/EIPS/eip-7892)

## ③ Transaction Gas Limit Cap

Fusaka는 단일 트랜잭션에 지정하는 `gasLimit`을 `16,777,216 (2^24) gas`로 제한한다.
하나의 트랜잭션이 블록 전체 연산 리소스를 독점해 발생하는 DoS 공격을 방지하고, 블록 내 트랜잭션 간 형평성 있게 가스를 할당하며, 극단적으로 긴 블록 검증 시간을 방지하여 노드 간 동기화를 원활하게 하기 위함이다.

실제 소비량이 더 적더라도 **지정한 `gasLimit` 자체가 상한을 만족해야 한다.** 예를 들어 실제 실행은 1,000,000 gas만 필요하더라도, 여유 있게 `gasLimit = 20,000,000`을 지정하면 거래 자체가 거부된다.

[EIP-7825: Transaction Gas Limit Cap](https://eips.ethereum.org/EIPS/eip-7825)

# 3. Glamsterdam

> 외부 미들웨어에 의존하던 블록 생성 체계를 L1 프로토콜로 내재화하며, EVM 연산 구조를 병렬 처리에 맞춰 개편



## ① ePBS (Enshrined Proposer-Builder Separation)

기존의 PBS 구조에서는 프로토콜 외부에서 MEV-Boost라는 미들웨어를 통해 proposer와 builder 분리를 구현하는 방식이다.

- MEV-Boost 미들웨어
  - MEV-Boost의 흐름을 단순화하면 아래와 같다.
  `builder가 relay에 블록 페이로드 및 입찰 제출 -> relay가 블록 유효성 검증 -> proposer가 blinded block 선택 -> relay가 페이로드 제공`
  - builder가 유효하지 않은 블록을 보내거나, proposer가 완성된 블록 내용을 미리 보고 탈취하는 등 여러 우려들이 배경에 있었다.
  - proposer와 builder 사이에 제3자 '**relay**'라는 중개자를 두고 신뢰하는 방식이다.
  - relay는 블록의 유효성을 검증 후 proposer에게 블록 페이로드 헤더와 입찰가를 보여주고, proposer가 서명하면 페이로드를 제공한다.

relay는 프로토콜 외부의 중앙화된 서버 형태로 운영되므로, 중앙화되거나 장애가 발생할 수 있다. 장애 시 다른 relay에 연결하면 되지만, 블록 제안 과정에서 리스크 요소로 취급된다.

EIP-7732 **ePBS**(Enshrined PBS)는 기존 MEV-Boost 구조의 relay를 없애고, relay가 수행하던 핵심 중개 역할을 이더리움 합의 레이어 내부 코드로 '내장(Enshrine)'한다.

[EIP-7732: Enshrined Proposer-Builder Separation](https://eips.ethereum.org/EIPS/eip-7732)

## ② BALs: EVM 병렬 처리의 기반

기존 EVM은 트랜잭션을 하나씩 순차적으로 실행해서 상태 변화를 적용했다. 트랜잭션을 실행하기 전에는 어떤 스토리지 슬롯에 접근해서 변경이 생길지 알 수 없었기 때문에, 노드의 CPU 코어가 여러 개여도 하나의 블록을 처리할 때는 멀티코어를 활용한 병렬 처리가 어려웠다.

BALs(Block Access Lists / EIP-7928)는 블록 builder가 블록을 조립할 때, **블록 단위**로 접근 대상(계정, 스토리지 슬롯 등)을 요약 정리한 해시를 블록 헤더, 바디에 포함시키는 방식이다. validator 노드는 블록을 전달받았을 때 BALs를 참조하여 상호 간에 스토리지 충돌이 없는 트랜잭션 그룹을 판별하고, 이를 CPU의 여러 코어에 분배하여 병렬로 실행할 수 있다.

```
            [ 병렬 작업 배분의 단순화된 예시 ]
                           │

   ┌───────────────────────┼───────────────────────┐
   ▼                       ▼                       ▼

  [ Group A ]             [ Group B ]             [ Group C ]
  Tx 1, Tx 3 (상태 A 접근)   Tx 2 (상태 B 접근)      Tx 4, Tx 5 (상태 C 접근)
  │                       │                       │
  Core 1 실행             Core 2 실행             Core 3 실행
  └───────────────────────┼───────────────────────┘
                          ▼
                    [ 상태 최종 적용 ]

```

[EIP-7928: Block Access Lists](https://eips.ethereum.org/EIPS/eip-7928)

## ③ Gas 모델 개편: 실행/상태 리소스 분리

Glamsterdam에서는 가스 수수료 메커니즘도 개편된다. 실행과 상태 생성에 사용되는 가스를 별도로 계량한다. Fusaka의 **EIP-7825** 상한을 실행 가스에 적용하면서, 전체 거래 상한 내에서 별도의 상태 가스 예산을 허용한다.

신규 계정 생성이나 스토리지 슬롯 할당처럼 노드의 디스크 용량을 영구적으로 차지하는 작업에 상대적으로 높은 가스 비용을 부과하여, 장기적인 상태 증가(State Bloat)를 억제하려는 설계다.

 [EIP-8037: State Creation Gas Cost Increase](https://eips.ethereum.org/EIPS/eip-8037)

# 4. Hegotá

> 거래 포함을 강화하고 네이티브 계정 추상화를 지원



## ① FOCIL (Fork-choice enforced Inclusion Lists)

블록 구성을 전문 builder에게 맡기면 validator의 부담은 줄어들지만, 소수의 builder가 블록 생산을 주도할 경우 트랜잭션의 블록 포함 여부를 결정하는 권한도 집중된다. 이들이 특정 거래를 반복적으로 제외하더라도, 나머지 거래가 유효하다면 기존 검증만으로는 이를 막기 어렵다. ePBS 역시 이러한 거래 선택 문제를 직접 해결하지는 않는다.

ePBS 체제에서는 고성능 builder가 특정 트랜잭션을 의도적으로 배제하거나 검열할 가능성이 존재한다. 이를 방지하기 위해 FOCIL이라는 정책이 도입된다.

FOCIL은 단일 proposer가 아닌 무작위로 선출된 여러 validator committee가 각자 메모리풀을 관찰하여 **반드시 포함되어야 할 트랜잭션 목록(Inclusion List)**을 작성한다.

FOCIL에서 블록의 유효성 검증은 attester의 투표 동작과 연동된다. attester 노드는 자신이 확보한 Inclusion List를 기준으로 builder가 제안한 블록이 요구 조건을 충족했는지 검증한다. 만약 builder가 해당 리스트의 트랜잭션을 정당한 사유 없이 배제했다면, attester는 해당 블록에 증명 투표를 하지 않는다. 투표를 받지 못한 블록은 포크 초이스 규칙에 의해 자연스럽게 체인의 canonical block으로 선택되지 못하고 탈락하는 구조다.

[EIP-7805: Fork-choice enforced Inclusion Lists (FOCIL)](https://eips.ethereum.org/EIPS/eip-7805)



## ② Frame Transactions: 가스 지불 승인을 포함한 네이티브 계정 추상화

ERC-4337은 온체인 EntryPoint와 별도 메모리풀·번들러를 결합해 스마트 계정을 지원한다. Pectra의 EIP-7702는 EOA가 변경·해제할 때까지 컨트랙트 코드에 실행을 위임하도록 한다. Hegotá의 Frame Transactions 제안은 계정 추상화를 네이티브 거래 형식으로 확장한다.

EIP-8141은 검증·가스 지불 승인·실행을 위한 여러 프레임을 순서대로 구성한다. 아래는 고정된 두 프레임 구조가 아니라 단순화한 흐름 예시다.

```

[ Frame Transaction (EIP-8141)의 단순화된 예시 ]
┌────────────────────────────────────────────────────────┐
│  1. Validation Frame                                   │
│     - 서명 검증 (P-256 / 패스키 등 커스텀 로직)               │
│     - 가스 지불 승인 (대납 및 선택적 토큰 정산 로직)       │
├────────────────────────────────────────────────────────┤
│  2. Execution Frame                                    │
│     - 실제 DApp 호출 및 상태 변경 연산                       │
└────────────────────────────────────────────────────────┘

```

- **Validation Frame**
  - 송신자를 대신해 작업을 실행하기 전에 계정의 서명·지출 한도 등 승인 로직을 실행한다. 검증은 포함 전 검사뿐 아니라 블록 실행 중에도 적용된다.
  - `APPROVE` 명령으로 실행, 가스 지불 또는 둘 모두를 승인한다. `True` 반환만으로 승인되는 것은 아니다.
- **Execution Frame**
  - 승인이 완료되면 실제로 토큰을 송금하거나 스마트 컨트랙트를 호출하는 로직이 실행된다.

프레임은 Fusaka의 P-256 프리컴파일을 포함한 커스텀 서명 검증과 제3자의 가스 대납 승인을 지원하며, ERC-4337의 별도 번들러 인프라를 필수로 요구하지 않는다. 프로토콜 가스비는 여전히 ETH로 지불하며, 대체 토큰 정산은 애플리케이션 로직으로 처리한다.

[EIP-8141: Frame Transactions](https://eips.ethereum.org/EIPS/eip-8141)

# 5. 확장 후에도 남는 과제

Fusaka, Glamsterdam, Hegotá로 이어지는 개편이 진행되더라도 이더리움 생태계에는 지속적으로 평가해야 할 과제들이 남아있다.

1. **builder 레이어의 집중화 문제**: ePBS를 통해 블록 제안 과정의 relay 의존성을 줄이더라도, 고성능 MEV 알고리즘과 대규모 자본을 가진 일부 전문 builder로 블록 생성 시장이 집중되는 현상은 여전히 존재한다.
2. **노드 운영 리소스 부담**: PeerDAS와 BALs는 효율을 개선하고, BPO는 검증된 단계별 용량 조정을 가능하게 한다. 처리량이 늘면 대역폭, CPU, 메모리 부담도 커질 수 있어 소규모 노드 운영에 대한 평가가 필요하다.
3. **L2 자체의 보안 및 탈중앙화 문제**: L1의 데이터 가용성과 실행 성능이 향상되는 것과 별개로, 각 L2 체인이 사용하는 sequencer의 탈중앙화 수준, Fraud/Validity Proof 시스템의 완성도는 L2 생태계 내부에서 별도로 검증하고 평가해야 하는 영역이다.

# 6. 정리

- **Fusaka**: PeerDAS와 BPO(EIP-7892)를 통해 L2용 **데이터 가용성 공간을 확장**하고, EIP-7825로 L1 연산 안전선을 설정한다.
- **Glamsterdam**: 포함 예정인 ePBS(EIP-7732)로 **proposer·builder 간 조율을 프로토콜에 내장**하고, BALs(EIP-7928) 및 가스 개편(EIP-8037)을 통해 **EVM 병렬 실행 기반**을 정비한다.
- **Hegotá**: 포함 예정인 FOCIL(EIP-7805)로 **검열 저항성 규칙**을 보완하고, Frame Transactions(EIP-8141)를 통해 **가스비 승인을 포함한 네이티브 계정 추상화 체계**를 정립한다.
