지난 주의 중심 흐름은 **보안 위험이 개별 애플리케이션에서 공통 인프라 계층으로 내려가고 있다는 점**이다. Cosmos EVM과 Ledger Secure SDK 사례는 여러 체인이나 앱이 공유하는 모듈 하나가 넓은 공격 표면을 만들 수 있음을 보여준다.

동시에 Monad와 TRON에서는 주소, 인증 수단, 실행 환경을 더 유연하게 분리하려는 움직임이 이어진다. Wallet 제품은 체인별 기능 차이만이 아니라 **인증 방식과 보안 상태를 독립된 capability로 모델링**할 필요가 커지고 있다.

## 1. Cosmos EVM 취약점이 실제 악용되며 6개 체인에 영향

Cosmos Labs의 [사후 분석](https://github.com/cosmos/security/blob/main/communications/cosmos_evm_GHSA-7g4w-cg88-2cq2_post_mortem.md)에 따르면 공격자는 8월 20일부터 25일까지 `GHSA-7g4w-cg88-2cq2`를 악용해 여러 Cosmos 기반 체인에서 자금을 탈취했다. 취약점은 Cosmos EVM의 공통 `StateDB`에 있던 balance underflow 검증 누락이었다. 특정 vesting·delegation 흐름에서 EVM이 계산하는 사용 가능 잔액이 wrap-around되어 실제로 존재하지 않는 잔액을 이동시킬 수 있었다.

영향 범위는 `<0.6.2`와 `0.7.0–0.7.1`이며, 수정은 `0.6.2`와 `0.7.2+`에 포함됐다. Cosmos 보안팀은 약 40개 체인과 대응을 조율했고, 실제로 6개 네트워크가 공격받았다고 밝혔다.

### 왜 중요한가

이번 사고는 modular chain에서 공통 모듈 하나가 여러 네트워크에 동시에 영향을 주는 **shared-module blast radius**를 보여준다. 개별 체인의 앱 코드가 안전하더라도 upstream 실행 계층의 회계 오류를 그대로 상속할 수 있다.

### Product / Engineering 관점

Wallet의 chain-support pipeline은 runtime과 module version을 호환성 정보만이 아니라 보안 정보로 취급해야 한다. registry를 기반으로 체인을 자동 노출한다면 취약한 `cosmos/evm` 버전, chain halt, 긴급 업그레이드, 일시적 disable 상태를 함께 전달할 수 있어야 한다.

### Follow-up

- 지원 중인 Cosmos EVM 체인의 deployed `cosmos/evm` 버전을 점검한다.
- 일반 chain metadata와 분리된 emergency warning·disable 경로를 설계한다.

## 2. Ledger 공통 SDK 취약점이 “표시한 내용과 서명한 내용”의 일치를 흔들다

Ledger의 [LSB-023](https://donjon.ledger.com/lsb/023/)은 사용자가 첫 번째 작업을 검토하는 동안 악성 host가 다른 APDU command를 끼워 넣을 수 있던 문제를 설명한다. 취약한 앱에서는 화면에 표시한 뒤에도 signing parameter가 바뀔 수 있어, 사용자가 Transaction A를 확인했지만 Transaction B의 parameter에 서명하는 상황이 가능했다. Ledger는 공개 시점까지 실제 악용 증거는 없다고 밝혔다.

핵심은 firmware보다 **shared Ledger Secure SDK**에 있었다는 점이다. 수정은 `v26.6.1`에 포함됐고, 영향을 받는 앱은 이 SDK로 다시 빌드되어 배포돼야 한다. firmware만 업데이트해서는 수정이 전달되지 않는다.

### 왜 중요한가

Hardware wallet의 device screen을 절대적 trust boundary로 간주할 수 없다는 사례다. host와 app 사이의 command sequencing, 그리고 검토 중 상태 전이가 같은 수준으로 중요해진다.

### Product / Engineering 관점

Wallet client는 엄격한 APDU sequencing과 명시적인 signing state machine을 가져야 한다. Ledger firmware version뿐 아니라 최소 지원 Ledger App version도 관리해야 한다. Swap, plugin, simulation, clear signing과 blind signing이 섞이는 흐름일수록 검증 범위가 넓어진다.

### Follow-up

- Ledger 연동에서 firmware와 app version을 각각 검증하는지 확인한다.
- 사용자 검토 이후 signing payload가 바뀌지 않는지 integration test로 확인한다.

## 3. Monad가 주소와 인증 수단을 분리하는 계정 모델을 제안

Monad는 **Flexible and Upgradeable Account Authentication** 초안을 공개했다. 이 설계는 account address를 유지한 채 그 주소를 제어하는 authenticator를 추가·교체·폐기할 수 있게 하는 방향이다. 보도된 초안은 key rotation, passkey, multisig recovery, social recovery, 그리고 post-quantum signature scheme으로의 전환을 염두에 둔다. 현재는 [초기 draft](https://cryptodaily.co.uk/2026/08/monad-wallet-key-rotation-without-address-change)이며 구현 specification과 합의 과정이 남아 있다.

### 왜 중요한가

일반적으로 이런 기능은 smart account나 account abstraction 계층에서 구현된다. Monad의 접근은 이를 protocol-level account model까지 내리려는 시도다. 주소는 지속적인 identity가 되고, authentication은 교체 가능한 구성으로 바뀐다.

### Product / Engineering 관점

Wallet은 장기적으로 account를 `address ↔ private key` 관계가 아니라 `address + authentication configuration`으로 다뤄야 할 수 있다. Recovery UX, key export, passkey, hardware signer, transaction authorization API를 더 독립적인 모듈로 유지하는 편이 유리하다.

### Follow-up

- recovery authority와 authentication 변경 delay를 확인한다.
- downgrade protection과 기존 EOA-compatible tooling의 해석 방식을 검토한다.

## 4. Firefox 악성 Wallet Extension 캠페인이 사칭 공격의 산업화를 보여주다

Socket의 [조사](https://www.socket.dev/blog/firefox-crypto-wallet-theft)는 코드와 인프라를 공유하는 77개의 Firefox extension identity를 추적했고, 이 중 40개에서 지갑 또는 credential 탈취 기능을 확인했다. 이들은 OKX, Rabby, TronLink 등을 사칭했으며, seed phrase와 private key를 수집하거나 원격 콘텐츠로 피싱 화면을 제공했다. Socket은 이 캠페인을 **Offside Wallet Theft Factory**로 부른다.

### 왜 중요한가

공격은 단순한 phishing website 복제를 넘어선다. 공격자는 기존 extension identity와 version history를 활용하고, open-source wallet 코드를 복제하며, 원격 인프라를 통해 동작을 교체한다. 공식 extension store에 등록됐다는 사실만으로는 충분한 신뢰 신호가 되기 어렵다.

### Product / Engineering 관점

Publisher authenticity 자체가 product surface가 된다. 공식 website에서 검증된 설치 링크를 제공하고, 공식 extension ID를 공개하며, 앱 안에서 설치 출처를 안내해야 한다. conflicting 또는 fake provider 탐지 역시 검토 대상이다.

### Follow-up

- 설치 funnel과 support 문서에 canonical extension ID가 명시돼 있는지 점검한다.
- extension이 초기화 과정에서 keyring·clipboard·seed phrase에 접근하는 경로를 위협 모델에 반영한다.

## 5. TRON이 EVM 호환성과 Passkey용 primitive를 확장

TRON의 mandatory node upgrade인 [GreatVoyage `v4.8.2 (Pyrrho)`](https://github.com/tronprotocol/java-tron/releases/tag/GreatVoyage-v4.8.2)는 TVM을 Ethereum Pectra·Osaka 실행 환경에 더 가깝게 맞춘다. 이번 릴리스에는 WebAuthn과 passkey, Apple Secure Enclave, Android Keystore에서 널리 쓰이는 `secp256r1`/P-256 curve의 signature verification precompile이 포함됐다. TRON의 [버전 문서](https://tronprotocol.github.io/documentation-en/releases/versions/v4.8.2/)도 Pectra·Osaka 대응과 관련 precompile 변경을 설명한다.

TRON은 address-less signature verification과 cross-chain messaging을 위한 interface도 제안하고 있다. [TIP-7913](https://github.com/tronprotocol/tips/issues/7913)은 다양한 signature verifier를, [TIP-7786](https://github.com/tronprotocol/tips/issues/7786)은 공통 cross-chain messaging gateway를 다룬다.

### 왜 중요한가

Ethereum이 아닌 체인도 완전히 독자적인 execution semantics를 유지하기보다 Ethereum-compatible primitive를 적극적으로 수용하고 있다. 이는 multichain wallet에서 chain 이름보다 capability를 중심으로 기능을 추상화해야 한다는 신호다.

### Product / Engineering 관점

`if (chain === "tron")` 같은 체인별 분기보다 `supportsPasskey`, `supportsEvmSigning`, `supportsSmartAccount`, `supportsCrossChainMessaging`처럼 capability를 표현하는 구조가 확장에 유리하다. TRON 지원은 EVM transaction·authentication abstraction을 재사용하고 얇은 chain-specific adapter를 두는 방식으로 설계할 여지가 커진다.

### Follow-up

- TRON integration에서 재사용 가능한 EVM signing·authentication 경계를 정의한다.
- passkey verification과 cross-chain messaging primitive의 실제 mainnet activation 상태를 추적한다.

## 이번 주 우선순위

가장 즉각적인 과제는 Cosmos EVM 취약점 점검이다. Cosmos SDK·EVM network를 자동으로 노출하거나 chain registry로 지원 체인을 관리하는 Wallet에서는 직접적인 architecture 이슈가 된다. 두 번째는 Ledger SDK 대응이다. Hardware wallet display를 신뢰 경계의 전부로 보던 가정을 다시 검토해야 한다.

더 큰 흐름은 Wallet identity와 key가 분리되고, Wallet UX가 passkey와 programmable authentication으로 이동하는 방향이다. 따라서 multichain wallet은 **chain representation → transaction execution → authentication/signing → security health state**를 하나의 chain type에 강하게 결합하지 않는 구조를 지향할 필요가 있다.

> 브리핑은 매주 월요일 Codex로 생성된 분석 자료를 기반으로 작성된다. 게재 전 블로그 운영자의 직접 검수 및 승인을 거친다.
